# ローカルセッション実測: コンテキスト使用量と compaction

計測日: 2026-11-05。ソース: `~/.claude/projects/*/*.jsonl`(読み取りのみ)。集計値だけを記載し、本文・パス・プロジェクト名は含めない。

各節は **全セッション** と **Opus 5.5 のみ** を並べる。Opus で標本が薄い箇所は「標本が少なすぎる数値」にまとめた。

1. **床は約 70k で、100k を超えた例はない。** ただし実測は圧縮前 200k 以上だけで、それ未満での床は未観測。100k 閾値の余地は約 30k(Opus 約 28k)で、ユーザーターン増分 p90 の半分に満たない。
2. **ターン間の圧縮では上限を厳密に保てない。** 超過の中央値は小さいが、裾が長い。リプレイの最大ピークは閾値の 1.36 倍(580k)から 7.89 倍(100k)に達した。原因は 1 リクエストの急増ではなく、1 ターン内の累積。ただしどの閾値の倍率 max も同じ 1 ターン(ピーク 789,250、1 ターンで約 74 万トークン増)で決まっている。典型値はエンジンターン越境の超過 p90 で約 85k〜200k。
3. **観測された圧縮の大半は 870k 由来ではない。** 8 割前後が「200k 以上で end_turn の約 54 分後」という放置型だった。観測値を現行方針の挙動として読まないこと。現行の 870k 圧縮に相当しうる manual は 1 件しかない。
4. **`input + cache_read + cache_creation` を usage のトップレベルで足すと誤る。** advisor を使うリクエストでは iterations が合算され、見かけ値が約 2 倍になる。本調査は最後の `type=message` iteration を使った(下の「文脈サイズの定義」)。
5. **mod に同じ誤差がある可能性。** `hooks/register.ts` 614 行目は usage のトップレベルを足している。渡される `TurnUsage` が transcript と同じ合算値なら、advisor 使用直後に文脈を過大評価する。未検証。

### サブエージェントの除外方法

1. glob の深さで除外した。`<project>/*.jsonl` だけを読むと `<project>/<session>/subagents/*.jsonl`(238 ファイル)は入らない。
2. 検証: 対象ファイルに `isSidechain=true` のレコードは 0 件。サブエージェント側の user/assistant レコードは 63,369 件すべて true。
3. `api-request.querySource` は `repl_main_thread` と `sdk` のみ。

### 文脈サイズの定義

- 依頼の式を、**最後の `type=message` iteration の usage** に適用した。iterations がないレコードだけトップレベルを使う。
- advisor ループのリクエスト(全体 191、Opus 183)では、トップレベルが前後 2 回の model iteration を合算している。例: 実値 約 168k に対して表示 約 335k。未補正のピーク max は 1,922,147 で、1M 窓を超える。
- 1 応答が複数レコードに分かれるため `requestId` で重複を除いた(40,557 レコード)。圧縮後に再掲される履歴やフォークも、全ファイル横断の重複除去で処理した。圧縮の境界も uuid で除去した(1 件)。
- `<synthetic>` とエラーメッセージ(103 件)は除外した。

### ターンの定義

- **ユーザーターン(依頼の定義):** `turnOrigin=human` で、meta、圧縮要約、ローカルコマンド出力を除いた user レコードの間。typed と queued を含む。
- **エンジンターン(感度分析):** `stop_reason` が `tool_use` 以外になるリクエストまで。task-notification や予約実行もここで区切れる。README の「main turn end」に対応すると解釈した。

**不確かな点:** `turnOrigin` がなく本文タグもない非 meta の user 文字列が 1,104 件ある(`cli` 4 セッション、うち 997 件が 1 セッション、すべて 2.1.304、長さ p50 約 2,400 字、ほぼ全文が相異なる)。このうち 792 件は人のプロンプトと同じ `promptId` を持つので、既存ターンの内側にあり新しいプロンプトではない。残り 312 件は人のプロンプトにない `promptId` を持つ。本文は見ていない。どちらも実プロンプトに数えていないので、残り 312 件が人の入力だった場合はユーザーターン数が過小になる。

## 4. ターン途中の越境(実測軌跡)

同一の圧縮区間内で、前のリクエストが閾値未満、当該リクエストが閾値以上の越境を数えた。

- **先頭:** ターン最初のリクエストで越え、その後も続いた。
- **途中:** 先頭でも最後でもないリクエストで越えた。
- **最終:** ターン最後のリクエストで越えた(ターン終端の判定でそのまま捕まえられる)。
- **先頭+途中率:** (先頭 + 途中) / 越境 n。前のターン終端は閾値未満なので、先頭の越境もターン終端の圧縮では止められない。
- **追加:** 越境後、ターン終了までのピーク - 越境時の文脈。先頭と途中の越境が対象。
- **超過:** ターン内ピーク - 閾値。全越境が対象。

## 5. 閾値別の圧縮回数(リプレイ)

### 前提

1. 実測の文脈増分(リクエスト間の差)を順に足す。増分は文脈サイズや圧縮の有無に依存しないとする。圧縮後の読み直しによる増加は入れていない。
2. 実際の圧縮をまたぐ差分は捨てる。実際の圧縮はなかったものとし、以下の規則だけで圧縮を発生させる。
3. エンジンターン終端で s ≥ T なら圧縮する。次のリクエストの文脈は床(母集団ごとの実測 p50)に固定し、その 1 回分の増分は加えない。
4. ターン途中で s ≥ 967k なら上限型の圧縮を起こす。
5. 放置型の規則: ターン終端で s ≥ 200k かつ、次のリクエストまで 53 分以上(または実データでその位置に放置型の圧縮があった)なら圧縮する。実測の 70% 程度しか発火しない規則を毎回発火させるため、やや多めに出る。
6. セッション最終ターンの圧縮も数える。

## 6. キャッシュ(リプレイ、トークンのみ)

料金は一次情報を確認していないため金額にしていない。read と write は単価が違うので、合計トークンの大小を金額の大小として読まないこと。

### 前提

- ヒット: read = 前回の文脈 × model iteration 数、write = 増分。
- 実データで read が前回文脈の半分未満だったリクエストはミスとして扱う(read はプレフィックス分の実測 p50 約 27.8k、残りを write)。
- リプレイの圧縮直後: read は実測 p50(全 27,774 / Opus 28,215)、残りを write。
- 圧縮要求 read: 圧縮時の文脈をそのまま 1 回読むと仮定した。圧縮要求は transcript に記録がなく、**未検証**。
- 要約 output: postTokens の p50(全 18,582 / Opus 19,435)× 回数で代用。
- 校正: 実軌跡を入力したとき、モデルの read は実測の 100.0%、write は 100.8%(Opus 100.0% / 100.3%)。これはキャッシュ式の校正で、閾値を変えた軌跡の正しさは示さない。
- 通常リクエストの output は閾値で変わらないとして除外した。サブエージェント分は含まない。

## 手法の限界

1. **期間と規模:** 約 33 日、1 利用者、`cli` 50 セッション。Opus は最多 1 セッションがリクエストの 36%、上位 5 セッションが read の 81%。一般化はできない。
2. **進行中のデータ:** 本セッションなどが書き込みを続ける transcript を読んだため、実行ごとに数件〜数十件変わる。本文の数値は最後の 1 回の実行に基づく(実行時点の差は 2 つの母集団で数秒)。
3. **打ち切り:** 実測ピーク、越境、増分は現在の圧縮挙動に影響されている。放置型が高文脈の区間を切るので、高閾値の越境は標本が減る。
4. **現行方針の未観測:** 870k の mod 圧縮はほぼ観測がない。870k の行はリプレイであり実測ではない。
5. **床の外挿:** 床の実測は圧縮前 200k 以上だけ。200k 未満では、保存される末尾の量や要約サイズが違う可能性がある。
6. **挙動の変化を未モデル化:** 圧縮後の再読、作業の分割、圧縮のターン内介入、利用者の行動変化、圧縮の品質低下は入っていない。
7. **放置型の規則:** 実測の発火率 約 70% に対し、リプレイでは毎回発火させる。機構は未確認で、将来の版で変わりうる。
8. **Opus の絞り込み:** リクエスト単位で Opus 以外を落とした。混在は 2 セッションで、落としたのは 1,051 リクエスト。そこでは前後の Opus リクエストの差をそのまま増分とした。Opus 以外がターンの終端だった場合、エンジンターンの区切りがずれる。床などの定数は Opus の値で再計算した。
9. **ターン分類:** 上記の未分類 1,104 件に左右される。エンジンターンを mod の発火単位とみなしたのは README の記述からの解釈で、mod の実行を追跡したものではない。
10. **キャッシュ:** 圧縮要求は未記録で read は推定。TTL の扱いは実データのミス判定と 60 分のギャップ規則による近似。サブエージェント分のキャッシュは含まない。

## 再現

集計スクリプトは本セッションの scratchpad の `logs/` にある。`measure.py` を実行すると全セッションの結果を、環境変数 `OPUS_ONLY=1` を付けると Opus のみの結果を出力する。パーセンタイルは最近傍順位法。文脈式とパーセンタイルに assert の自己チェックがある。リプレイ本体は単体テストなしで、校正値との比較のみ。

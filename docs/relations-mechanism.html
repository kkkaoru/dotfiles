pi-relations-extension — how it works

One graph per pi session: what the session is, what it planned, what it ran, and what it produced. Stored in Pi Durable beside the session file, written by a tool or a shell command, read back in the same shape.

The shape of the thing

relations toolinside pi: add / link / unlink / show / list
cli.tsfrom a shell: same actions, same graph
↓
apply(graph, params)pure: returns the next graph, or the same one when nothing changes
answer(graph, params)pure: the text this call prints
↓ save · flush
Pi Durable storeone document dotfiles.relations v1, holding the graph as JSON
<session>.relations-durable/JSONL files beside the session, like the loop, tmux and timeline sidecars

The data model

A node is a thing, an edge is a statement about two things. There is nothing else.

node  = kind:ref          "tmux:pi-tmux-abc-1"
edge  = from + relation + to [+ note]
        "session:01a1fcbf"  "ran"  "tmux:pi-tmux-abc-1"  "panic log parsing"
kindnamesexample ref
sessionthe pi session doing the work01a1fcbf
goala persistent goalrelations
loopa self-paced looptb-watch
tmuxa detached jobpi-tmux-abc-1
timelinea task treerelations
taskone task in a treet3
doca document kept in Gitdocs/report.md
filea path in the working treetools/pi-relations-extension

A relation is a lower-case verb joined by hyphens — produced, planned, ran, evidenced-by, implemented-by. A ref may contain colons; the first colon splits the kind from the ref.

Writing, step by step

  1. Open. mkdir <session>.relations-durable, take a lock on it, open the JSONL storage with fsync, then open a Pi Durable harness over it.
  2. Restore. Read the one document; parse its state string back into a graph, refusing anything that is not a valid graph. No document yet means an empty graph.
  3. Apply. add or link or unlink builds a new graph and never mutates the old one, so “did anything change?” is a reference comparison.
  4. Save. Serialise now, so a later edit cannot race the write, then queue the commit that puts the string in the document.
  5. Flush. Wait for the queue; a failed commit is reported to the user and re-thrown, never swallowed.
  6. Answer. Render the new graph (or one node with both directions of its edges).
  7. Close. Close the harness and drop the lock, in a finally, so a bad id cannot leave the sidecar held.

Steps 1 and 7 bracket every call, including the CLI's. Eight separate bun cli.ts invocations in a row therefore accumulate one graph — that is the whole persistence test.

What the design buys

propertyhow
Idempotent writesadding a known node changes nothing; linking the same edge twice only updates its note. The stored graph is untouched when apply returns the same object.
Refuses nonsensean unknown kind, an empty ref, a relation that is not a lower-case word, or a stored document that does not parse — all throw with a message naming the field.
Survives a resumethe sidecar sits beside the session file, so reopening the session finds the graph where the loop and tmux sidecars already are.
No session, no problemwithout a session file the graph lives in memory only — the tool still answers, nothing is written.
Honest failurea failed commit notifies Relations storage stopped: … and fails the call; the process does not pretend the edge was recorded.

Using it

relations list                                      # the whole graph
relations show session:01a1fcbf                     # one node, both directions
relations link session:01a1fcbf ran tmux:pi-tmux-1  # creates either endpoint if missing
relations add doc:docs/report.md --label "the report"

bun tools/pi-relations-extension/cli.ts list        # from a shell
bun tools/pi-relations-extension/cli.ts link session:$PI_SESSION_ID produced doc:docs/report.md

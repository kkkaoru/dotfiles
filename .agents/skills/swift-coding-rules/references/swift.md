# Swift Coding Rules

This is the only normative Swift rule set for agents. Every requirement has one Rule ID and appears once. These are strict repository policies informed by Swift documentation, not an official Swift style standard. MUST, MUST NOT, and prohibitions are mandatory; preferences apply only among alternatives satisfying every mandatory rule. Research context and version caveats are in [sources.md](sources.md).

## Repository and verification

- **SW01 Repository setup:** Use the configured Swift/Xcode toolchain, Swift language mode, SDK, deployment targets, package resolution, project layout, and scripts. Inspect `Package.swift`, Xcode build settings, and CI as applicable; compiler version, language mode, and SDK availability are separate constraints. Do not introduce a second build system, dependency manager, or unnecessary dependency.
- **SW02 Implementation planning:** Before implementing, build a thorough plan covering affected contracts, ownership and isolation boundaries, compatibility, and verification.
- **SW03 Verification toolchain:** After each logical change, run focused checks and then the configured build, format-check, lint, and tests. For SwiftPM use the repository's `swift build` and `swift test` workflow; for Xcode use its scheme, configuration, and destination with `xcodebuild`. Use the existing formatter/linter configuration: `swift format` (swiftlang/swift-format), SwiftFormat, and SwiftLint are distinct tools, not interchangeable commands. Require zero build, concurrency, lint, and test warnings/errors in the affected targets, reproduce expected behavior, and inspect actual command results. Required checks that fail or cannot run block verified completion: report the blocker, including pre-existing failures, rather than claiming success or silently reducing verification scope.
- **SW04 Quality integrity:** MUST NOT suppress diagnostics, disable lint rules, skip/cancel tests to hide failures, downgrade assertions to warning issues, or weaken language/concurrency settings or quality gates. This includes warning-control attributes, known-issue annotations, baseline exclusions, and retry-until-green workflows. Any exception to this rule set requires the user's explicit approval before implementation, a documented technical necessity, the narrowest scope, compensating tests, and a removal condition; do not infer approval from this skill or a general implementation request.

## Types, values, and APIs

- **SW05 Domain models:** Prefer structs and enums with associated values to encode valid states, units, and errors. Use classes when identity, shared reference semantics, inheritance, or framework requirements justify them; use `final` when subclassing is not intended.
- **SW06 Mutation and constants:** Prefer `let`; use `var` for necessary, narrowly scoped mutation. Replace magic numbers with meaningfully named constants, using type-scoped `static let` for shared type constants and local constants for genuinely local values. Avoid unprotected mutable global/static state; a `let` reference does not make its referent immutable.
- **SW07 Optional values:** Model absence with optionals and narrow with `guard let`, `if let`, or pattern matching. MUST NOT introduce force unwraps, forced casts (`as!`), or implicitly unwrapped optionals in production or tests. Unavoidable generated/framework contracts require the SW04 exception process and documented initialization/lifetime guarantees; handwritten convenience is never justification. Use `??` only for a contract-defined fallback, never to hide invalid or missing required input.
- **SW08 Abstraction and typing:** Prefer concrete types and small protocols; use generics or `some Protocol` to preserve type relationships, and `any Protocol` when heterogeneous runtime storage is required. MUST NOT introduce `Any`, `AnyObject`, or unchecked type erasure except for an unavoidable interoperability signature approved under SW04; immediately validate and convert boundary values into concrete domain types. Prefer conditional casts with explicit failure handling over casting assumptions. Do not require redundant annotations where inference preserves a clear contract.
- **SW09 API design and access:** Follow Swift API Design Guidelines: prioritize clarity at the call site, meaningful argument labels, `UpperCamelCase` types/protocols and `lowerCamelCase` members. Choose the narrowest appropriate access (`private`, `fileprivate`, `internal`, `package`, `public`, or `open`); do not expose implementation details by default. Document public contracts and observable side effects.
- **SW10 Exhaustiveness and availability:** Use exhaustive `switch` for owned enums; do not hide new cases behind an unnecessary `default`. Handle resilient external enums with `@unknown default` when required. Gate platform APIs with appropriate availability checks/annotations and compile-time platform/import checks; never assume a new compiler makes a newer OS API available.

## Functions and control flow

- **SW11 Function cohesion:** Keep functions focused and non-test code as DRY as possible. Keep `@main`, command entry points, and application lifecycle handlers as thin orchestration layers; extract reusable business logic from UI and framework callbacks.
- **SW12 Branching and iteration:** Reduce nesting with `guard`, early returns, and pattern matching. Use simple conditional expressions only when clearer; never nest ternaries. Use `map`, `compactMap`, `filter`, or `reduce` for clear transformations, not side effects or clever accumulator mutation. Use loops when clearer, avoid deeply nested loops, and name reusable sort comparators separately. Do not discard invalid data with `compactMap` unless omission is the contract.
- **SW13 Parameters:** Group three or more related options into a typed configuration value when it clarifies invariants and call sites; do not add a wrapper solely to satisfy an argument count. Keep required dependencies explicit rather than hiding them in singletons or ambient state.

## Errors, resources, and memory

- **SW14 Error handling:** Use structured `Error` types and `throws`/`async throws` for recoverable failures; use `Result` when an API needs an error-bearing value. Use typed throws only when a fixed failure type is a useful supported contract. Catch errors specifically and preserve useful underlying causes. MUST NOT introduce empty `catch`, `try?`, `try!`, or silent fallback on failure; model intentional absence explicitly and handle every error path. MUST NOT introduce `fatalError`, `assertionFailure`, `preconditionFailure`, assertions, or preconditions as production control flow. Unavoidable invariant traps require SW04 approval, a proof of the invariant, and boundary tests.
- **SW15 Data boundaries:** Validate external input before constructing domain values. Prefer typed `Codable` models for structured serialization, and explicitly handle malformed data, missing fields, encoding, numeric bounds, and HTTP status codes; successful decoding alone is not domain validation. Use URL/path APIs instead of concatenating path strings, and respect Unicode-aware `String` indexing.
- **SW16 Resource lifecycle:** Scope files, locks, observers, streams, and temporary resources with deterministic cleanup (`defer`, scoped APIs, or explicit lifecycle methods). Do not rely solely on `deinit` for timely cleanup. Use async cleanup in `defer` only if supported by the configured compiler; otherwise provide an explicit success/error/cancellation cleanup path. Minimize and buffer I/O; parallelize only independent operations with bounded concurrency and no ordering or shared-file hazards.
- **SW17 ARC and captures:** Make reference ownership explicit and prevent cycles involving delegates, escaping closures, subscriptions, and tasks. Use `weak` when the referent may disappear; new `unowned` captures/references require SW04 approval and a documented proof of lifetime safety; do not add `[weak self]` mechanically when the operation must retain its owner. Account for tasks retaining `self` across suspension and for cycles that prevent `deinit`-based cancellation.
- **SW18 Unsafe interoperability:** Prefer safe collections and supported safe views such as `Span` over pointer manipulation. MUST NOT introduce unsafe pointers, `unsafeBitCast`, `unsafeDowncast`, `Unmanaged`, unsafe continuations, or other unchecked memory operations without SW04 approval. Isolate approved unavoidable pointer/C/C++ boundaries behind safe APIs, document allocation, lifetime, bounds, alignment, binding, and ownership invariants, and test edge cases. Never escape pointers from scoped `withUnsafe…` APIs or assume they survive an `await`. Adopt strict memory-safety checking only through the project's supported configuration, not by silently changing the toolchain baseline.

## Concurrency and isolation

- **SW19 Concurrency configuration:** Inspect the target's default actor isolation, strict-concurrency checking, and upcoming-feature settings before editing async code. Swift 6 language mode enforces data-race safety, but does not itself imply default `MainActor` isolation. Swift 6.2 caller-isolated nonisolated async behavior is configuration-dependent; never assume every `async` function runs on a background executor. Use supported `@concurrent` only when concurrent execution is intended and safe.
- **SW20 State isolation:** Protect shared mutable state with actors, global actors, or a justified scoped synchronization primitive. Keep UI state and UI updates on `MainActor` where the framework requires it. Choose isolation based on ownership, not to silence errors by annotating unrelated code. Keep lock scopes short and never hold a blocking lock across `await`.
- **SW21 Sendability:** Use checked `Sendable` conformances and `@Sendable` closures where cross-isolation sharing requires them. Distinguish safe sharing from ownership transfer using supported `sending` APIs. Do not introduce `@unchecked Sendable`, `nonisolated(unsafe)`, `@preconcurrency` imports, or isolation assumptions as compiler-error workarounds; unavoidable interoperability escape hatches require explicit approval, documented safety invariants, and focused tests.
- **SW22 Structured concurrency:** Prefer `async let` for a fixed set of independent child operations and task groups for dynamic work. Bound fan-out instead of creating a task per element in unbounded input. Use unstructured `Task` only at a necessary lifecycle/API boundary with an explicit owner, retained handle, observed completion/errors, and cancellation/join policy. Fire-and-forget work and discarded throwing-task handles are prohibited. New `Task.detached` requires SW04 approval and proof that structured concurrency or an owned actor cannot satisfy the requirement; unstructured tasks do not automatically gain structured parent cancellation.
- **SW23 Cancellation:** Treat cancellation as cooperative control flow. Check it in long-running work and before avoidable expensive work, propagate cancellation according to the API contract, and clean up resources. Do not retry cancellation or report it as an ordinary failure. Synchronize state shared with cancellation handlers and test cancellation races.
- **SW24 Reentrancy:** Treat every `await` as a potential interleaving point. Restore invariants before suspension and revalidate state afterward when needed; actor isolation does not make a multi-await operation atomic. Prevent stale results from overwriting newer requests using explicit identity/version checks or another documented strategy.
- **SW25 Execution boundaries:** Use `async` for actual asynchronous work or a required protocol/API contract. Keep blocking I/O and expensive synchronous work off UI isolation and cooperative executors using an appropriate bounded execution facility or native async API. `Task {}` can inherit actor isolation and `Task.detached` still uses the cooperative pool; neither automatically makes blocking code safe. Never bridge async work with semaphore waits, blocking sleeps, or synchronous dispatch onto the current executor.
- **SW26 Callback bridges:** Prefer native async APIs; when bridging callbacks, use checked continuations and ensure exactly one resume on every completing success/error path. Design cancellation, synchronous callbacks, and concurrent completion explicitly so they cannot leak or double-resume a continuation. For `AsyncStream`/`AsyncThrowingStream`, define buffering/backpressure behavior and stop the producer on termination.

## UI, organization, and diagnostics

- **SW27 UI ownership:** For SwiftUI work, keep `body` declarative and free of side effects or expensive computation. Preserve stable view/model identity and choose state/observation wrappers according to ownership and deployment support; do not create a second source of truth. Tie asynchronous loading to an explicit lifecycle such as `.task(id:)` and handle cancellation/stale results. Do not migrate an existing observation architecture merely because a newer API exists.
- **SW28 Source organization:** Keep files, modules, and extensions cohesive. Place imports first and supporting type declarations before free-function implementations; within types, group stored state, initialization, methods, and conformances consistently with the repository. Do not force unrelated types into a single file to satisfy declaration ordering. Remove dead code, unused imports/dependencies, and obsolete compatibility branches rather than masking warnings with underscore-prefixed locals; `_` is appropriate for genuinely ignored results or required unused parameters.
- **SW29 Documentation and diagnostics:** Write comments, DocC documentation, logs, and developer-facing errors in English, explaining contracts, rationale, and invariants rather than restating syntax. Follow the app's localization policy for user-facing text. Never log credentials or sensitive user data; use the configured logging system and privacy controls.
- **SW30 Performance:** Measure before introducing low-level ownership features, unsafe storage, custom executors, macros, specialization, or forced inlining. Preserve value semantics and avoid unnecessary allocation/copying, but do not trade verified correctness and readability for speculative optimization. Version-gate new features such as noncopyable containers and new iteration APIs.

## Tests and coverage

- **SW31 Test ownership:** When creating, editing, or deleting a non-test Swift file, add or update related tests for the affected behavior, public contracts, and data models. Follow the repository's test targets/layout; for manifest-only changes verify affected package builds and tests rather than inventing a unit test for `Package.swift`.
- **SW32 Test framework:** Use the existing test framework. For a new project on a supported Swift 6 toolchain, prefer built-in Swift Testing (`import Testing`, `@Test`, `#expect`, `#require`) for unit tests without adding a package dependency. Preserve XCTest where needed for existing suites, UI automation, or performance measurement; coexistence does not justify mixing assertion/lifecycle APIs inside a test without confirmed toolchain support.
- **SW33 Test clarity:** Prefer explicit, independent cases with literal expected outcomes; do not compute expected values using production logic. Avoid DRY helpers that hide the behavior under test, assertions inside loops, and deeply nested suites. Use native parameterized tests with explicit input/expected case data for genuinely identical behavior instead of manual loops. Use `#require` or the framework's throwing unwrap for prerequisites rather than force unwraps.
- **SW34 Test isolation:** Keep tests deterministic and fast using injected clocks, clients, temporary resources, and test doubles for network, filesystem, environment, and process dependencies. Swift Testing runs tests in parallel by default: avoid shared mutable fixtures and ordering assumptions. Use serialization only for a documented unavoidable shared resource, not to conceal races. Await observable completion instead of sleeping for guessed durations; use supported time limits for bounded async tests.
- **SW35 Test scenarios:** Cover success, invalid/missing input, boundary values, error propagation, resource cleanup, and changed concurrency contracts, including cancellation, reentrancy, and stale-result handling. Keep integration tests for real boundary behavior separate from fast isolated tests. For changed concurrent code run Thread Sanitizer on a supported target; for approved unsafe/interop memory changes run Address Sanitizer on a supported target, in separate compatible configurations. A clean sanitizer run supplements, never proves, correctness. Unsupported required verification must be reported as a blocker or explicitly approved limitation under SW04.
- **SW36 Coverage:** Require at least 95% line and function coverage for every changed testable source file, and at least 95% branch coverage where supported by the configured toolchain. Existing lower thresholds do not waive this requirement; never lower existing gates or use project-wide averages to hide gaps. Use the configured SwiftPM `swift test --enable-code-coverage` or Xcode coverage workflow and inspect file-level reports, not just test exit status. Missing tooling, unmeasurable files/platforms, unreachable branches, and generated/framework-only code need a documented scope assessment and SW04 approval for any exemption; do not exclude handwritten business logic or modify gates without approval. Coverage does not replace the behavioral scenarios in SW35.
- **SW37 Rules review:** After implementation, automatically review every applicable Rule ID against the actual diff. Before declaring verified completion, report the exact verification commands/results, file-level coverage, relevant sanitizer results, and explicitly approved exceptions; no applicable unresolved violation or missing required check may be presented as complete.

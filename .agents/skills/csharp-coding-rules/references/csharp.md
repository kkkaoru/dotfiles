# C# Coding Rules

This is the only normative C# rule set for agents, including Unity projects. Every requirement has one Rule ID and appears once. These are strict repository policies informed by .NET and Unity documentation, not an official C# or Unity style standard. MUST, MUST NOT, and prohibitions are mandatory; preferences apply only among alternatives satisfying every mandatory rule. Research context and version caveats are in [sources.md](sources.md).

A repository is a **Unity project** when `ProjectSettings/ProjectVersion.txt` exists. In a Unity project, apply every rule; rules marked "Unity: see CSxx" are refined by the named Unity rule, which takes precedence for that point only.

## Repository and verification

- **CS01 Repository setup:** Use the repository's configured .NET SDK (`global.json`), target frameworks, `LangVersion`, solution/project layout, Central Package Management, and scripts. Compiler language version, target framework or API profile, and runtime API availability are separate constraints; verify each before using a feature. MUST NOT introduce a second build system, package manager, or any new dependency without the user's approval. Unity: see CS34 and CS35.
- **CS02 Implementation planning:** Before implementing, build a thorough plan covering affected public contracts, nullability, serialization, async and threading boundaries, allocation behavior, compatibility, and verification.
- **CS03 Verification toolchain:** After each logical change, run focused checks and then the configured build, format check (`dotnet format --verify-no-changes` or the configured formatter such as CSharpier), analyzers, and tests. Require zero compiler, nullable, analyzer, and test warnings/errors in the affected projects, reproduce expected behavior, and inspect actual command results and logs. Required checks that fail or cannot run block verified completion: report the blocker, including pre-existing failures, rather than claiming success or silently reducing verification scope. Unity: see CS34.
- **CS04 Quality integrity:** MUST NOT add `#pragma warning disable`, `[SuppressMessage]`, `.editorconfig` or ruleset severity downgrades, `<NoWarn>`/`-nowarn`, the null-forgiving operator (`!`) anywhere including `= null!` initializers, `#nullable disable`, skipped or ignored tests (`Skip`, `[Ignore]`, `[Explicit]`), `LogAssert.ignoreFailingMessages = true`, coverage exclusions, retry-until-green workflows, or weaker `TreatWarningsAsErrors`, analysis level, analyzer packages, or coverage gates. Any exception to this rule set requires the user's explicit approval before implementation, a documented technical necessity, the narrowest scope, compensating tests, and a removal condition; do not infer approval from this skill or a general implementation request.

## Types, values, and APIs

- **CS05 Nullable reference types:** Nullable reference types MUST be enabled for new and changed code through the project's configured mechanism (`<Nullable>enable</Nullable>`, or in Unity the repository's `csc.rsp` or per-file `#nullable enable` convention). Model absence with `T?` and narrow with guard clauses or pattern matching. Validate every required argument of public and internal APIs at entry. Use `??` only for a contract-defined fallback, never to hide invalid or missing required input. Unity: see CS38 for `UnityEngine.Object`.
- **CS06 Domain models:** Encode valid states, units, and identifiers with dedicated types (`readonly struct`, enums, sealed classes, or records where supported) instead of loosely related primitives. Classes MUST be `sealed` unless designed and documented for inheritance. MUST NOT use `bool` or `int` flags where an enum or distinct type expresses the state.
- **CS07 Immutability and constants:** Fields MUST be `readonly` unless mutation is required; expose read-only properties and read-only collection interfaces at API boundaries, never mutable internal collections. Replace every magic number and string with a `const` or `static readonly` member named for its meaning; MUST NOT define shared constants inside methods. MUST NOT introduce mutable static state without CS04 approval; Unity: see CS42.
- **CS08 Unsafe typing:** MUST NOT introduce `dynamic`, `object`-typed domain values, unchecked direct casts, `as` without an immediate null check, or reflection-based dispatch. Use generics, interfaces, and `is`/`switch` patterns, and handle the non-matching case explicitly. Use `var` only when the type is evident from the right-hand side.
- **CS09 Abstraction:** Use concrete types by default. Introduce an interface, base class, generic, or source generator only for demonstrated duplication, a required test seam, or a required boundary, and state which in the plan. MUST NOT add an interface whose only purpose is to mirror a single implementation.
- **CS10 API design and access:** Follow .NET naming guidelines: `PascalCase` for types, members, and constants, `camelCase` for parameters and locals, `_camelCase` for private fields, and an `I` prefix for interfaces. Every type and member MUST use the narrowest workable access; do not expose implementation details. Document every public and protected member with XML documentation comments, including thrown exceptions and observable side effects.
- **CS11 Exhaustiveness:** Use `switch` expressions with patterns and handle every owned enum value explicitly; use a discard arm only to throw for undefined values, never to hide new cases. Validate externally supplied or deserialized enum values before use.

## Functions and control flow

- **CS12 Function cohesion:** Keep methods focused, reuse production logic, and keep non-test code as DRY as possible. Keep `Main`, top-level statements, controllers, hosted services, and Unity message methods as thin orchestration layers with as few steps as possible; extract business logic into plain C# types so it is testable without a host or engine.
- **CS13 Branching:** Reduce nesting with guard clauses, early returns, and pattern matching; nesting deeper than two levels inside a method requires refactoring. Use conditional expressions only for clear, simple values and never nest or chain them. Replace repeated `if`/`else if` or `switch` dispatch with a `switch` expression or a typed dictionary when that is clearer. MUST NOT use `goto` or `#region`.
- **CS14 Iteration and LINQ:** Use LINQ for clear, side-effect-free transformations outside hot paths and loops when mutation, short-circuiting, or stateful control flow is clearer. Avoid double or deeper loop nesting inside a single method. MUST NOT enumerate an `IEnumerable<T>` more than once; materialize with `ToList`/`ToArray` only when needed. Define reusable comparers or key selectors separately from the sort call. Unity: see CS41.
- **CS15 Parameters:** Group three or more cohesive parameters into a typed options type when it clarifies invariants and call sites. Keep required dependencies explicit through constructor or initializer injection; MUST NOT use service locators, static singletons, or ambient state for dependencies.

## Errors, resources, and memory

- **CS16 Exceptions:** Throw specific exception types and catch the narrowest type that can be handled. MUST NOT write empty `catch` blocks, catch `Exception`/`SystemException` outside a documented top-level boundary that logs and terminates or reports the failure, or use `throw ex;` (use `throw;`). Preserve causes with `innerException`. MUST NOT use exceptions for expected outcomes; use `Try…` patterns or result types.
- **CS17 Data boundaries:** Validate all external input (files, network, user input, deserialized data, save data) before constructing domain values. Use typed serializer models, and explicitly handle malformed data, missing fields, numeric bounds, versioning, culture (`CultureInfo.InvariantCulture` for machine formats), string comparison (explicit `StringComparison`), and HTTP status codes. Use `Path`/`Uri` APIs instead of string concatenation and parameterized queries instead of string-built SQL.
- **CS18 Resource lifecycle:** Dispose every owned `IDisposable`/`IAsyncDisposable` deterministically with `using` declarations, `using` statements, or `await using`. MUST NOT rely on finalizers for cleanup. Reuse HTTP clients (`IHttpClientFactory` or a long-lived instance; in Unity, the repository's `UnityWebRequest` wrapper with disposal) instead of creating one per request. Minimize file reads and writes, and run independent I/O concurrently only when ordering is unnecessary. Unity: see CS39.
- **CS19 Unsafe code:** Prefer `Span<T>`, `Memory<T>`, and safe collections. MUST NOT introduce `unsafe` blocks, pointers, `Unsafe`/`MemoryMarshal` reinterpretation, or P/Invoke without CS04 approval. Isolate approved native interop behind safe APIs, document lifetime, bounds, and ownership invariants, use `SafeHandle` where available, and test edge cases.

## Async and concurrency

- **CS20 Async correctness:** Use `async`/`await` only for actual asynchronous work. MUST NOT introduce `async void` except for framework event handlers that cannot return a task (never Unity message methods; see CS40), and MUST NOT block on async code with `.Result`, `.Wait()`, or `GetAwaiter().GetResult()`. Name asynchronous methods with the `Async` suffix and await each `ValueTask` or pooled awaitable exactly once. Follow the repository's `ConfigureAwait` policy consistently; Unity: see CS40.
- **CS21 Cancellation:** Every asynchronous operation that can outlive its caller or run long MUST accept a `CancellationToken` as its last parameter and pass it through every call. Treat `OperationCanceledException` as cancellation, not ordinary failure, and do not retry or log it as an error. Clean up resources on cancellation.
- **CS22 Task ownership:** MUST NOT introduce fire-and-forget tasks or discarded task results. Every task needs an owner that observes completion and exceptions. Use `Task.WhenAll` for a fixed set of independent operations and bounded concurrency (`Parallel.ForEachAsync` with `MaxDegreeOfParallelism`, `Channel<T>`, or `SemaphoreSlim`) for dynamic input. MUST NOT use `Task.Run` to wrap I/O-bound work or to hide synchronous work in library APIs.
- **CS23 Shared state:** Protect shared mutable state with immutable data, `lock`, `Interlocked`, or concurrent collections. Keep lock scopes short and never `await` while holding a lock. MUST NOT lock on `this`, types, or strings. UI and engine APIs MUST be called only from the thread the framework requires; Unity: see CS39.

## Organization and diagnostics

- **CS24 Source organization:** Every type MUST be in a namespace matching the folder or assembly structure; use file-scoped namespaces when the language version supports them. Place one top-level type per file, with the file named after the type. Place `using` directives at the top; use `global using` only in a single dedicated file when the repository already does so. Within a type, order constants, fields, constructors, properties, and methods consistently with the repository.
- **CS25 Unused code:** Remove unused types, members, variables, `using` directives, dependencies, empty methods, and obsolete compatibility branches instead of silencing tooling. Use the discard `_` only for genuinely ignored results or required unused parameters. MUST NOT leave commented-out code.
- **CS26 Documentation and diagnostics:** Write comments, XML documentation, logs, and exception messages in English, explaining contracts, rationale, and invariants rather than restating syntax. Use the configured logging abstraction with structured message templates rather than string interpolation. MUST NOT log credentials or sensitive user data. Unity: see CS43.
- **CS27 Performance:** Measure (BenchmarkDotNet, or the Unity Profiler/Profile Analyzer) before introducing `Span`-heavy code, pooling, `stackalloc`, struct layout control, or aggressive inlining, and record the measurement in the change description. Avoid unnecessary allocations, boxing, and repeated string concatenation, but do not trade verified correctness and readability for speculative optimization.

## Tests and coverage

- **CS28 Test ownership:** When creating, editing, or deleting a non-test C# file, add or update related tests for the affected behavior, public contracts, serialized data, and data models, following the repository's test projects and naming. For project-file-only changes, verify affected builds and tests rather than inventing unit tests.
- **CS29 Test framework:** Use the repository's existing test framework (xUnit, NUnit, MSTest, or the Unity Test Framework), assertion style, and mocking library. MUST NOT introduce another runner, assertion library, or mocking framework.
- **CS30 Test clarity:** Do not write DRY test code. Write explicit, independent cases with literal expected outcomes; MUST NOT compute expected values using production logic. Ban loops in tests and assertions inside loops. Use the framework's native parameterized tests (`[Theory]`/`[InlineData]`, `[TestCase]`, `[DataRow]`) with explicit literal case data only for genuinely identical behavior. Minimize nested test classes, and assert complete outcomes rather than partial containment checks.
- **CS31 Test isolation:** Keep tests deterministic and fast by injecting clocks (`TimeProvider` where available, otherwise a repository clock interface), HTTP handler stubs, temporary directories, and test doubles for filesystem, clock, environment, process, and network dependencies. MUST NOT share mutable fixtures or assume test order. MUST NOT wait with `Task.Delay`, `Thread.Sleep`, or guessed durations; await observable completion with a bounded timeout.
- **CS32 Test scenarios:** Cover success, null/invalid/missing input, boundary values, exception propagation, disposal, serialization round trips, and changed async contracts, including cancellation. Keep integration tests for real boundary behavior separate from fast isolated tests.
- **CS33 Coverage:** Require at least 95% line coverage and 95% branch coverage for every changed testable source file using the configured collector (for example `dotnet test --collect:"XPlat Code Coverage"` or coverlet). Existing lower thresholds do not waive this requirement; never lower gates or use project-wide averages to hide gaps. Inspect file-level reports, not just test exit status. `[ExcludeFromCodeCoverage]` or filter exclusions for handwritten logic require CS04 approval. Unity: see CS51.

## Unity projects

- **CS34 Unity toolchain and verification:** Use the editor version in `ProjectSettings/ProjectVersion.txt` and the packages pinned in `Packages/manifest.json` and `packages-lock.json`; MUST NOT upgrade the editor or packages without approval. Unity generates `.csproj`/`.sln` files: MUST NOT hand-edit or commit them, and configure compilation only through `.asmdef`, `.asmref`, `csc.rsp`, and Player Settings. Verify with the configured scripts or Unity batch mode: `-runTests -testPlatform EditMode` and `-testPlatform PlayMode` with `-testResults`, plus a player build or script compilation for every shipped platform and scripting backend (including IL2CPP) so that `#if` branches and stripping are compiled. Inspect test results and the editor/build log; any compiler, analyzer (including Microsoft.Unity.Analyzers when configured), or console warning or error in changed code blocks completion.
- **CS35 Unity language and API availability:** Determine the project's C# version, API Compatibility Level, and scripting backend before using a language or BCL feature. Mono-based Unity versions compile C# 9.0 with documented gaps (for example init-only setters, covariant returns, and module initializers are unsupported) against .NET Standard 2.1 or .NET Framework profiles; C# 10+ features such as file-scoped namespaces, `record struct`, and `global using`, and .NET 6+ APIs such as `ArgumentNullException.ThrowIfNull`, `TimeProvider`, and `System.Threading.Lock` are then unavailable. MUST NOT add polyfills such as `IsExternalInit` without approval, and never use records in Unity-serialized types. CoreCLR-based versions change these limits; re-verify against the project's Unity documentation.
- **CS36 Assets, meta files, and serialized renames:** Commit each asset's and folder's `.meta` file with it; MUST NOT delete, regenerate, or edit GUIDs. Move or rename assets together with their `.meta` files. Script files MUST contain exactly one `MonoBehaviour` or `ScriptableObject` type whose name matches the filename. Renaming a serialized field MUST add `[FormerlySerializedAs]`; moving or renaming a type used with `[SerializeReference]` MUST add `[MovedFrom]`. MUST NOT hand-edit scene, prefab, or asset YAML except for verified trivial changes with user approval.
- **CS37 Serialized fields:** MUST NOT declare public fields on Unity objects. Use `[SerializeField] private` fields exposed through read-only properties or methods. Serialized fields are not constructor-initialized: MUST NOT silence nullable warnings with `= null!`; declare required references as `T?` and validate them in `OnValidate` (editor) and `Awake` (runtime), failing loudly with an exception or error and disabling the component; after validation, read them only through narrowed locals or non-nullable fields assigned in `Awake`. Serialized types MUST be Unity-serializable; do not rely on serialization of properties, dictionaries, interfaces without `[SerializeReference]`, or records.
- **CS38 UnityEngine.Object null semantics:** For `UnityEngine.Object`-derived values, MUST NOT use `?.`, `??`, `??=`, `is null`, `is not null`, `is { }`, or `ReferenceEquals`; these bypass Unity's destroyed-object check. Use `== null`, `!= null`, or the implicit bool conversion, and `TryGetComponent` for lookups. Treat a destroyed object as absent.
- **CS39 Lifecycle and main thread:** Initialize self-owned state in `Awake`, subscribe in `OnEnable` and unsubscribe in the matching `OnDisable`, and resolve cross-object references in `Start` or explicit initialization; MUST NOT depend on undeclared cross-object `Awake` order or use Script Execution Order without approval. MUST NOT call Unity APIs from constructors, field initializers, finalizers, or background threads; move background work to the Job System or `Awaitable.BackgroundThreadAsync` and return with `Awaitable.MainThreadAsync` (or the repository's equivalent). Release every owned engine resource in `OnDisable`/`OnDestroy`: event subscriptions, Addressables handles, `NativeContainer`s, `RenderTexture`s, and runtime-created materials, meshes, and textures. MUST NOT use `DestroyImmediate` at runtime.
- **CS40 Unity async model:** Use the repository's async model (`Awaitable`, UniTask, or coroutines) and MUST NOT introduce a second one. MUST NOT declare `async void` Unity message methods (`Start`, `Update`, `OnEnable`, and others); delegate to an owned async method whose completion and exceptions are observed. Bind every operation to `destroyCancellationToken` or an owned `CancellationTokenSource` cancelled in `OnDisable`/`OnDestroy`. Await each `Awaitable` exactly once. MUST NOT use `Task.Delay`, `Thread.Sleep`, or `ConfigureAwait(false)` in code that touches Unity APIs, and state whether waits use scaled or unscaled time. Stop owned coroutines on disable; MUST NOT start or stop coroutines by string name.
- **CS41 Frame budget and allocations:** Per-frame paths (`Update`, `LateUpdate`, `FixedUpdate`, `OnGUI`, per-frame callbacks, and jobs) MUST NOT allocate managed memory in steady state: no LINQ, capturing lambdas, boxing, `params` arrays, string concatenation or interpolation, new collections, or per-frame `new WaitForSeconds`. Cache `GetComponent` results, `Camera.main`, and `Animator`/`Shader` property IDs (`Animator.StringToHash`, `Shader.PropertyToID`); use `CompareTag`, non-allocating physics queries with reused buffers, and object pooling. Remove empty Unity message methods. Verify changed hot paths with the Profiler's GC Alloc column or a performance test.
- **CS42 Banned Unity APIs and static state:** MUST NOT introduce `SendMessage`, `BroadcastMessage`, `Invoke`/`InvokeRepeating` by name, `GameObject.Find*`, `FindObjectOfType`/`FindObjectsOfType`/`FindAnyObjectByType`/`FindFirstObjectByType` in runtime code, new `Resources` folder loading, `DontDestroyOnLoad` singletons, or `OnGUI` runtime UI without approval; use serialized references, explicit injection, or Addressables. Because Enter Play Mode settings can skip domain reload, every approved static field and static event MUST be reset in a `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]` method. MUST NOT mutate `ScriptableObject` assets at runtime; copy runtime state into instances.
- **CS43 Unity logging:** MUST NOT add `Debug.Log*` calls to shipped runtime code paths except through the repository's logging wrapper, which MUST strip verbose logs from release builds via `[Conditional]` or defines. Pass the context object to log calls when available. Errors MUST use `Debug.LogError`/`LogException` or the wrapper's error level, never `Debug.Log`.
- **CS44 Physics, time, and input:** Apply forces and `Rigidbody` changes in `FixedUpdate` with `Time.fixedDeltaTime`; MUST NOT move a `Rigidbody` by setting `transform` (use `MovePosition`/`MoveRotation`). Scale frame-dependent motion by `Time.deltaTime` in `Update`. Read input in `Update` or through the configured Input System callbacks, never in `FixedUpdate`.
- **CS45 Assemblies and editor isolation:** All new code MUST belong to an assembly definition; MUST NOT add code to the predefined `Assembly-CSharp` assemblies. Place editor code in editor-only assemblies (`includePlatforms: ["Editor"]`); runtime assemblies MUST NOT reference `UnityEditor`, and `#if UNITY_EDITOR` blocks in runtime code require approval and minimal scope. Declare references explicitly, keep the dependency graph acyclic, and put engine-independent logic in assemblies with `noEngineReferences` where feasible.
- **CS46 Platform defines and AOT:** Isolate platform `#if` branches (`UNITY_IOS`, `UNITY_ANDROID`, `UNITY_WEBGL`, and others) in small adapter types and compile every branch during verification. Code MUST be IL2CPP/AOT-safe: MUST NOT use `System.Reflection.Emit`, runtime code generation, or unbounded generic virtual methods over value types. Reflection requires CS04 approval and preservation via `[Preserve]` or `link.xml`, verified in a stripped IL2CPP build. WebGL targets MUST NOT use threads.
- **CS47 Data-oriented code:** In Jobs, Burst, and ECS code, use only blittable data and `NativeContainer`s with explicit `Allocator` and disposal, declare `[ReadOnly]`/`[WriteOnly]` access, and complete every scheduled `JobHandle` before reading results or disposing inputs. MUST NOT disable safety checks or use `[NativeDisableContainerSafetyRestriction]`/`[NativeDisableParallelForRestriction]` without CS04 approval.
- **CS48 Unity test layout:** Use the Unity Test Framework with test assemblies constrained by `UNITY_INCLUDE_TESTS` and separate EditMode and PlayMode assemblies. Put logic in plain C# types tested in EditMode; use PlayMode only for lifecycle, physics, rendering, or scene integration. MUST NOT test through `Find*`, scene-name lookups, or production singletons.
- **CS49 Unity test behavior:** In `[UnityTest]` coroutines, wait for observable conditions with an explicit frame or time limit, never for guessed `WaitForSeconds` durations. Destroy every created `GameObject` and asset and dispose native containers in `TearDown`/`UnityTearDown`. Unexpected error or exception logs MUST fail the test; expect intentional logs with `LogAssert.Expect`. Use `Time.timeScale` or injected clocks deterministically and restore global state afterwards.
- **CS50 Unity performance verification:** For changes to hot paths, loading, or memory, record a before/after measurement with the Profiler, Memory Profiler, or the Performance Testing package on the target platform or a documented proxy. A Play Mode run in the editor alone does not prove player performance.
- **CS51 Unity coverage:** Use the Code Coverage package (`com.unity.testtools.codecoverage`) with EditMode and PlayMode tests. Branch coverage is not implemented in that package, so require at least 95% line coverage and full coverage of every changed public method for each changed testable runtime source file, and cover every branch with an explicit test case reviewed against the diff. Assembly or path filters MUST NOT exclude handwritten logic without CS04 approval.

## Completion

- **CS52 Rules review:** After implementation, automatically review every applicable Rule ID against the actual diff. Before declaring verified completion, report the exact verification commands/results, file-level coverage, profiling evidence when required, and explicitly approved exceptions; no applicable unresolved violation or missing required check may be presented as complete.

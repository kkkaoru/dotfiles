pi-relations-extension の仕組み

pi のセッション 1 つにつきグラフ 1 枚。そのセッションが何で、何を計画し、何を走らせ、何を生んだか。保存先はセッション ファイルの隣の Pi Durable。書くのはツールかシェルコマンド、読むのは同じ形で。

全体像

relations ツールpi の中から: add / link / unlink / show / list
cli.tsシェルから: 同じ操作、同じグラフ
↓
apply(graph, params)純粋関数。次のグラフを返す。変化が無ければ同じオブジェクトをそのまま返す
answer(graph, params)純粋関数。この呼び出しが表示するテキスト
↓ save · flush
Pi Durable ストアドキュメント 1 つ dotfiles.relations v1 に、グラフを JSON 文字列で
<session>.relations-durable/セッションの隣の JSONL。loop・tmux・timeline のサイドカーと同じ並び

データモデル

ノードは「物」、エッジは「2 つの物についての文」。それ以外は何も無い。

node  = kind:ref          "tmux:pi-tmux-abc-1"
edge  = from + relation + to [+ note]
        "session:01a1fcbf"  "ran"  "tmux:pi-tmux-abc-1"  "パニックログの解析"
kind指すものref の例
session作業している pi セッション01a1fcbf
goal持続するゴールrelations
loop自走するループtb-watch
tmux切り離されたジョブpi-tmux-abc-1
timelineタスクツリーrelations
taskツリー内のタスク 1 つt3
docGit で管理する文書docs/report.md
file作業ツリーのパスtools/pi-relations-extension

関係名は小文字の語をハイフンでつないだもの — produced、planned、ran、evidenced-by、implemented-by。ref の中にコロンは入ってよい。最初のコロンだけが kind と ref の境目。

グラフの例

依存関係の表し方

「A が B に依存する」は専用の仕組みではなく、向きのあるエッジ 1 本。関係名が依存の種類を言い、矢印の向きが「どちらが前提か」を言う。ツールは関係名を予約語として扱わないので、語彙は自分で決めてよい。

知りたいこと書くエッジ
この作業は何を狙ったかsession:… → pursued → goal:…
ゴールをどう回したかgoal:… → tracked-by → loop:…
何を走らせたかsession:… → ran → tmux:…
何が生まれたかtmux:… → produced → doc:…
何を根拠にしたかdoc:… → evidenced-by → file:…
計画を何が実装したかtimeline:… → implemented-by → file:…
順番の前提task:t3 → blocked-by → task:t2
片方が消えたら困るtmux:… → depends-on → file:…

関係名に制約は「小文字で始まり、小文字・数字・ハイフンのみ」だけ。だから blocked-by も depends-on も同じ重さで並ぶ。意味の強さを区別したいなら、関係名の語彙を決めて README に書くのが唯一の方法。

自動で記録される関係

ゴール・ループ・tmux・タイムラインのツールが終わるたび、その呼び出しが含む関係がグラフに足されます。手で link する必要はありません。拡張は tool_result を 1 つ購読し、ツール名・引数・返り値から edgesForCall で関係を決め、recordEdges で書きます。

ツール足す関係note
start_goal get_goal goal_waitsession —pursued→ goal:<id>目的（160 文字まで）
update_goalsession —pursued→ goal と goal —completed|blocked→ sessionreason
loop_wakeupsession —looped→ loop:<session id>reason
loop_completesession —looped→ loop と loop —completed→ sessionreason
tmux_execsession —ran→ tmux:<tmux のセッション名>実行したコマンド
tmux_check_insession —ran→ tmux:<tmux のセッション名>なし
timelinesession —planned→ timeline:<tree>。add なら timeline —contains→ task:<tree>/<id> もtitle

書くときの約束

  • 冪等。同じ関係を 2 度書いても 1 本で、グラフが変わらなければコミットもしない。
  • note は 160 文字で切る。目的やコマンドの全文を毎コミットに載せないため。
  • ループは 1 セッション 1 本なので loop:<session id>。タイムラインの既定ツリーは tree-1 で、呼び出しが tree を指定すればそちら。
  • 失敗は黙る。ロック競合やディスク不足は捨て、ツール呼び出しは成功したまま。保存エラーを見たいときは relations ツールで書く。

記録しないもの

  • 推測。ゴールがまだ無ければ id が無いので何も書かない。起動に失敗した tmux はセッション名が無いので何も書かない。
  • 関係の解釈。足すだけで、閉包・循環検出・順序付けはしない。show は 1 ホップだけ。
  • 上の 8 ツール以外の呼び出し。ファイルやドキュメントの関係は今までどおり link で書く。

グラフの型とユースケース

同じ語彙で、形の違うグラフが書ける。どれも「ノード + 向きのあるエッジ」だけで、専用の図式は無い。

ハブ — 1 セッションが何を持っているか

運用の一周 — 自動と手動の境目

タスクツリー — 入れ子と順序

共有ノード — 複数のセッションが同じ物を指す

書かない場合 — エッジ 0 本

読み方 — show は 1 ホップ

書き込みの流れ

アクションごとの挙動

読み取りは 1 バイトも書かない。書き込みは「グラフが別物になったときだけ」起きる — apply が同じオブジェクトを返したら save も呼ばない。

action必須書くか返すもの
addidノードが新規、または label が変わったときだけグラフ全体
linkfrom relation toその 3 つ組が新規、または note が変わったときだけ。端点が無ければ裸のノードとして作るグラフ全体
unlinkfrom relation to一致するエッジがあったときだけ。無ければ無視（エラーにしない）グラフ全体
showid書かない。ノードが無ければ No node … で失敗そのノード 1 つ＋出るエッジと入るエッジ
list無し書かない全ノードを id 昇順に、各ノードの出るエッジだけ

入力の正規化と検証

対象決まり
id前後の空白を落とし、最初のコロンで kind と ref に割る。ref の中のコロンはそのまま。kind が既知で ref が空でなければ通る
relation^[a-z][a-z0-9-]*$。空白は落とす。大文字・空白・アンダースコアは拒む
label / note前後の空白を落とし、空文字は「無し」として捨てる（"" は保存されない）
同じ 3 つ組の linkエッジを置き換える。note を省けば note も消える。位置は末尾に移る
保存内容の読み戻しノードのキーと ref の不一致、未知の kind、配列でない edges — どれも TypeError で開くこと自体が失敗する

失敗したときの挙動

起きること結果
コミットが失敗利用者に 1 度だけ通知（Relations storage stopped: …）、flush がその失敗を投げ、呼び出しは失敗する。以降の保存はキューで捨てられる（同じ通知を繰り返さない）
close のときすでに通知済みの失敗を投げ直さない。ハーネスは必ず閉じ、ロックも必ず離す
ツール呼び出しと CLI が同時サイドカーのロックで直列化。3 回までリトライし、取れなければその呼び出しが失敗する（黙って上書きしない）
前のプロセスが残したロックproper-lockfile が古いロックを引き継ぐ。だから異常終了のあとでも次の呼び出しは通る
セッション ファイルが無いメモリ上のストアで動く。ツールは答えるが、終われば何も残らない
閉じたストアへの保存Pi Durable relations store is closed. で失敗する

ツールの応答には details として { nodes, edges } の件数も付く。だから「書けたつもり」ではなく、件数が増えたことを呼び出し側で確かめられる。

保存場所

設計がもたらすもの

性質どうやって
書き込みが冪等既知のノードをもう一度 add しても何も変わらない。同じエッジを 2 回 link しても note が更新されるだけ。apply が同じオブジェクトを返したら、保存自体を行わない。
でたらめを拒む未知の kind、空の ref、小文字の語でない関係名、壊れた保存内容 — どれも該当フィールド名を挙げて例外になる。
再開に耐えるサイドカーはセッション ファイルの隣。loop や tmux のサイドカーと同じ扱いなので、再開したセッションがそのまま読める。
セッションが無くても動くセッション ファイルが無ければグラフはメモリのみ。ツールは答えるが、ディスクには何も残らない。
失敗を隠さないコミットが失敗すれば Relations storage stopped: … を通知し、呼び出しも失敗させる。書けたふりをしない。

使い方

relations list                                      # グラフ全体
relations show session:01a1fcbf                     # 1 ノードと両方向
relations link session:01a1fcbf ran tmux:pi-tmux-1  # 端点が無ければ作る
relations add doc:docs/report.md --label "報告書"

bun tools/pi-relations-extension/cli.ts list        # シェルから
bun tools/pi-relations-extension/cli.ts link session:$PI_SESSION_ID produced doc:docs/report.md

check bun run check — 整形、lint、型検査、テスト 79 件、カバレッジ 99.2% statements / 98.75% branches（ファイル単位で 95% の下限）。
